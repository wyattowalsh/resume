## Artifact model

This repo intentionally ships three different resume artifacts from one canonical data source:

| Artifact               | Route     | Job                                                                                                                           |
| ---------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Online resume          | `/`       | Broadest public surface with richer project depth, subtle scroll progress, skill-only popovers, and footer downloads.         |
| Editorial print resume | `/full`   | Local-only 2-page PDF/PNG visual artifact plus semantic DOCX export with calmer pacing and more supporting detail.            |
| Distilled print resume | `/single` | Local-only 1-page PDF/PNG visual artifact plus semantic DOCX export with a stricter linear reading path for safer extraction. |

Only `/` is canonical and indexable. The production SSR layer blocks `/full` and `/single`, `robots.txt` disallows those paths plus `/downloads/`, and `sitemap.xml` lists only `https://resume.w4w.dev/`. Static PDF/DOCX downloads are intentional user downloads, not search landing pages; keep them omitted from the sitemap and mirror the noindex policy with static-file headers if hosting support is added later.

## Data flow

1. `assets/data/resume.json` is the canonical fact source.
2. `assets/data/variants/site.json`, `full.json`, and `single.json` curate that data per artifact.
3. `src/lib/resume-data.ts` resolves and validates each variant before rendering.
4. Dedicated layouts (`SiteResumeLayout`, `FullResumeLayout`, `SingleResumeLayout`) own artifact-specific composition.
5. `src/lib/artifact-specs.ts` also defines the explicit DOCX policy contract under each artifact spec's `docx` field.
6. `assets/data/skill-details.json` adds web-only skill popover display data in the `{ name, desc, icon, links }` shape, guarded from leaking into generated PDF/DOCX artifacts.
7. `assets/data/skill-icons.json`, `assets/data/skill-section-icons.json`, and `public/skill-icons/` provide the web-only local icon layer for skill chips and section headings. Skill-chip icons should be compact original symbols or source-traced product icons, not wide wordmarks or banner logos.
8. `src/lib/resume-downloads.ts` centralizes the public footer download labels, paths, and accessibility labels.

The DOCX intent is deliberate: both exports retain the basics summary, selected work summaries, and project highlights for ATS richness, while the 1-page PDF can still suppress visible role summaries for layout density. The same DOCX policy also defines whether Projects start on a fresh DOCX page (`full`) or continue inline (`single`) and whether project stacks are emitted into DOCX text (`full` includes stack keywords, `single` stays compact).

## Web interaction contract

- The top progress indicator is noninteractive and uses a Radix Progress primitive wrapped in `src/components/ui/progress.tsx`.
- The progress indicator appears only after the header sentinel leaves the viewport and updates via `IntersectionObserver`; it does not poll `scrollY` or attach scroll handlers.
- Skills are the only popover surface. Work and project proof should remain directly visible in the page content, not hidden behind role/project dialogs.
- All visible skill chips are keyboard-accessible popover triggers. Curated skills use the simplified `name`, `desc`, `icon`, `links` shape in `assets/data/skill-details.json`; uncatalogued skills still open lightweight category-context cards so the UI has no static skill pills.
- Skill icons must stay readable at trigger size. Prefer oldschool, classic, or original icon-only marks where they fit; replace wide wordmarks and banners with compact favicons, devicons, or explicit concept icons.
- Project action pills use contextual leading icons for GitHub, Kaggle, docs, and live/external links while preserving the trailing external-link indicator.
- Public resume downloads live in the bottom footer only.

## Validation workflow

- `pnpm build`
- `pnpm exec tsc --noEmit`
- `pnpm test`
- `pnpm lint`
- `pnpm check:docs`
- `pnpm check:artifacts`
- `pnpm check:artifacts:current`

For SEO-only edits, run `pnpm exec vitest run src/lib/site.test.ts` to validate the canonical title, description, social image, canonical URL, and JSON-LD graph shape.

`pnpm check:artifacts` regenerates `/full` and `/single`, syncs `public/downloads/`, verifies page counts and letter sizing, checks generated/public download hash parity, checks curated content presence across PDF and DOCX artifacts, confirms the full PDF remains exactly 2 pages, and confirms the `/single` PDF still extracts in the intended `Experience → Skills → Projects → Education` order.

`pnpm check:artifacts:current` is the audit path for the artifacts already on disk. It runs `pnpm build:script` and then executes the checker with `RESUME_ARTIFACT_RECENCY=skip`, which skips only the generated-artifact freshness gate while keeping the same PDF, DOCX, parity, and content assertions.

The same gate also verifies ATS-oriented parseability for generated artifacts and static public downloads:

- PDFs must remain tagged, unencrypted, JavaScript-free, and image-free.
- Fonts must be embedded Unicode fonts, with Type 3 fonts rejected.
- `pdfjs-dist` and Poppler `pdftotext` must extract contiguous contact fields, profile URLs, section headings, selected work entries, skill groups, keywords, and project descriptions.
- DOCX `word/document.xml` must expose parseable contact fields, section headings, selected entries, skills, education, certifications, and project descriptions.
- DOCX relationships must retain contact, profile, and project hyperlinks, including project live-site links when a variant includes a `url`.
- DOCX stack expectations must follow each artifact spec's `docx.showProjectStacks` policy.
- Web-only skill-detail copy and reference URLs from `assets/data/skill-details.json` must stay out of generated and public PDF/DOCX artifacts.
- Required headings must not degrade into letter-spaced text such as `E X P E R I E N C E`.

Keep the checker aligned with `src/lib/artifact-specs.ts`: the `docx` policy fields are the source of truth for whether DOCX summaries and project highlights must be present.

Local runs need Poppler (`pdfinfo`, `pdffonts`, `pdftotext`, `pdfimages`) on `PATH`. If Puppeteer cannot find Chrome automatically, run with `PUPPETEER_EXECUTABLE_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"`.

## CI behavior

The GitHub Actions workflow installs root dependencies and docs dependencies from their separate lockfiles, installs `poppler-utils`, runs the same core validation chain, builds the docs app with `pnpm check:docs`, executes `pnpm check:artifacts` so generated files and `public/downloads/` are checked in one synced pass, and uploads the generated PDFs/PNGs/DOCX files as workflow artifacts for inspection. Its final clean-tree check ignores regenerated tracked binary downloads because PDF/DOCX byte output can vary across macOS and Linux while the content, layout, and same-run generated/public parity checks remain enforced.

The release workflow mirrors practical root quality gates before upload: build scripts, production build, typecheck, lint, tests, `pnpm check:artifacts`, and a SHA-256 manifest. Release uploads include generated PDFs, DOCX files, PNG previews, and `SHA256SUMS.txt`.

## Visual and professional QA

Use CI artifacts or local generated PNG/PDF outputs for visual QA whenever layout, typography, section budgets, icons, or public resume facts change. Confirm the web route remains a professional person/entity page for Wyatt Walsh as a Senior AI/ML Engineer in New York City, with the same context reflected in metadata, JSON-LD, visible copy, and the print artifacts.

Skill icons and popover descriptions are web-only. Keep icon provenance in the icon data pipeline, keep generated PDFs image-free, preserve all visible skill chips as interactive triggers, and preserve the artifact checker rule that tooltip-only skill descriptions and reference URLs stay out of PDF/DOCX exports.

The skill-icon regression tests also protect chip readability. `src/lib/skill-details.test.ts` rejects known wide wordmark sources and pins compact replacements for wordmark-prone skills such as AMPS, `q`, Tableau, XGBoost, Pandera, Go, Bash, and Market Data Systems. After icon-pipeline edits, run `pnpm sync:skill-icons`, visually check the affected popovers on `/`, run `pnpm test -- src/lib/skill-details.test.ts`, and use `pnpm check:artifacts` when generated/public downloads are touched.
